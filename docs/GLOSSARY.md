# Глоссарий проекта

Термин → что это → зачем нам / где в проекте. Пополняется по ходу работы.

## Процесс

- **Conventional Commits** — формат сообщений коммитов `тип(область): что сделано`, например `feat(quick-add): парсер дат`. Позволяет автоматически собирать CHANGELOG.
- **Контекст (context window)** — «оперативная память» языковой модели: всё, что она сейчас видит (диалог, прочитанные файлы, вывод команд). Ограничен; чем он полнее, тем хуже модель следует инструкциям. Поэтому документы проекта короткие и разбиты по темам.

## Архитектура и синхронизация

- **Local-first** — подход, при котором данные живут на устройстве пользователя, приложение полностью работает офлайн, а синхронизация — дополнение, а не основа. Противоположность «тонкому клиенту» к серверу.
- **P2P (peer-to-peer)** — устройства обмениваются данными напрямую, без центрального сервера. У нас два варианта: через общую папку (устройства не общаются, но читают файлы друг друга) и напрямую по локальной сети.
- **CRDT (Conflict-free Replicated Data Type)** — структура данных, спроектированная так, что две копии, изменённые независимо, всегда можно слить в одно состояние без конфликтов и без «главного». Основа нашей синхронизации.
- **Op-log (журнал операций)** — вместо хранения «текущего состояния» храним список всех изменений («поле X задачи Y стало Z в момент T»). Состояние — результат применения журнала. Удобно пересылать: каждое устройство отдаёт только новые записи.
- **LWW (Last-Writer-Wins)** — правило разрешения конфликтов: побеждает изменение с более поздней меткой времени. У нас применяется к каждому полю отдельно, поэтому правка названия на телефоне и приоритета на ПК не затирают друг друга.
- **HLC (Hybrid Logical Clock)** — «гибридные логические часы»: метка времени, составленная из обычного времени, счётчика и идентификатора устройства. Гарантирует уникальный и правильный порядок событий даже при расхождении часов на устройствах.
- **Tombstone («надгробие»)** — вместо физического удаления записи ставим флаг «удалено». Иначе другое устройство, не знавшее об удалении, воскресило бы запись при синхронизации.
- **Идемпотентность** — свойство операции, при котором повторное выполнение не меняет результат. Применить одну и ту же op дважды = применить один раз. Критично, когда файлы могут прочитаться повторно.
- **Проекция (materialized view)** — таблицы `tasks`, `projects` и т.д., построенные из журнала для быстрых запросов. Их можно удалить и пересобрать (`rebuildFromOps`).
- **Fractional index** — способ хранить порядок элементов строковыми ключами, между любыми двумя из которых всегда можно вставить новый («a» < «am» < «b»). При перетаскивании меняется ключ одного элемента, а не номера всех, поэтому два устройства не конфликтуют.
- **UUIDv7** — уникальный идентификатор, в начале которого закодировано время создания. Сортируется хронологически и не требует центрального счётчика.
- **NDJSON** — текстовый формат «один JSON-объект на строку». Удобен для append-only журналов: дописали строку — файл остался валидным.
- **Снапшот (snapshot)** — полный слепок состояния узла на момент времени. Новое устройство читает снапшот вместо всего журнала с начала времён.
- **Компакция** — удаление старых записей журнала, уже учтённых в снапшоте, чтобы папка не росла бесконечно.
- **mDNS** — протокол обнаружения устройств в локальной сети по имени службы без настройки (как принтеры и Chromecast). Для LAN-синхронизации.
- **WebSocket** — постоянное двустороннее соединение между двумя программами по сети. Для обмена ops по LAN.
- **HMAC** — подпись сообщения общим секретом: получатель проверяет, что сообщение от сопряжённого устройства и не изменено.
- **Монорепозиторий / `packages/`** — несколько пакетов в одном репозитории. `packages/oplog_sync` — ядро синхронизации как отдельный чистый Dart-пакет, который можно тестировать без Flutter и однажды опубликовать.

## Flutter и Dart

- **Flutter** — фреймворк Google для приложений под Android, iOS, Windows, macOS, Linux и web из одного кода на Dart. Сам рисует интерфейс, поэтому выглядит одинаково на всех платформах.
- **Dart** — язык Flutter. Строгая типизация, null-safety, компилируется в нативный код.
- **Виджет** — любой элемент интерфейса во Flutter (кнопка, список, отступ, целый экран). Интерфейс — дерево виджетов.
- **Material 3** — текущая дизайн-система Google; набор готовых виджетов и правил (цвета, формы, типографика).
- **drift** — библиотека для работы с SQLite в Dart: таблицы описываются кодом, запросы проверяются компилятором, результаты можно «слушать» как поток (`watch`) и UI обновляется сам.
- **SQLite** — встраиваемая база данных в одном файле; стандарт для мобильных и десктопных приложений.
- **Riverpod** — библиотека управления состоянием: «провайдеры» хранят данные и логику, виджеты подписываются на них и перерисовываются при изменении.
- **Кодогенерация / build_runner** — инструмент, который по аннотациям в коде создаёт файлы `*.g.dart`, `*.freezed.dart`. Их не правят руками (хук блокирует); правят источник и запускают `dart run build_runner build -d`.
- **freezed** — генератор неизменяемых (immutable) классов-моделей с `copyWith`, сравнением и сериализацией.
- **go_router** — библиотека навигации: экраны как URL-подобные маршруты; нужна для переходов из уведомлений и виджетов.
- **l10n / ARB** — локализация: тексты интерфейса лежат в файлах `app_ru.arb`, `app_en.arb`, код обращается к ним по ключам.
- **RRULE** — стандарт (из iCalendar) записи правил повторения: `FREQ=WEEKLY;BYDAY=MO,WE`. Храним повторения в нём.
- **Widget test / integration test** — тесты Flutter: первый проверяет один виджет в памяти, второй гоняет настоящее приложение на устройстве.
- **flutter analyze** — статический анализатор: находит ошибки и подозрительный код до запуска.

## Платформы

- **SAF (Storage Access Framework)** — механизм Android для доступа к папкам вне приложения (включая Google Drive) через системный диалог выбора. Так Android-версия получает папку синхронизации.
- **WorkManager** — планировщик фоновой работы Android, который переживает перезапуск и учитывает батарею. Для периодической синхронизации.
- **Точные будильники (exact alarms)** — разрешение Android будить приложение в точное время. Нужно для напоминаний «в 9:00», а не «примерно в 9».
- **Toast (Windows)** — системное всплывающее уведомление Windows в правом нижнем углу с кнопками действий.
- **MSIX** — формат установщика Windows-приложений; нужен сертификат подписи (для себя — самоподписанный).
- **Трей (system tray)** — область значков у часов Windows; приложение «живёт» там свёрнутым и показывает напоминания.
- **Syncthing** — программа синхронизации папок между своими устройствами напрямую, без облака. Один из вариантов «общей папки».

## Окружение разработчика

- **PATH** — переменная окружения Windows со списком папок, в которых система ищет исполняемые файлы. Мы добавили `C:\src\flutter\bin`, чтобы команды `flutter` и `dart` работали из любой папки. Новые окна терминала подхватывают изменение, уже открытые — нет.
- **flutter doctor** — команда самопроверки Flutter: показывает, какие инструменты найдены (SDK, Visual Studio, Android SDK, устройства) и чего не хватает. Запускаем после установки и при странных ошибках сборки.
- **Workload (Visual Studio)** — набор компонентов установщика Visual Studio под задачу. Нам нужен «Desktop development with C++»: компилятор MSVC, CMake и Windows SDK, которыми Flutter собирает Windows-версию. Сама IDE не используется.
- **Android cmdline-tools** — консольные утилиты Android SDK (`sdkmanager`, `avdmanager`). Flutter через них проверяет и устанавливает компоненты SDK; ставятся из SDK Manager в Android Studio.
- **Android SDK licenses** — лицензии Google на компоненты SDK; их нужно принять один раз (`flutter doctor --android-licenses`), иначе сборка APK откажется работать.
- **ADB-авторизация** — при первом подключении телефона по USB с включённой отладкой Android спрашивает, доверять ли этому компьютеру. Пока не нажато «Разрешить», Flutter видит устройство, но не может на него ставить приложение.
- **Windows PowerShell 5.1 и PowerShell 7** — две разные программы. 5.1 встроена в Windows (`powershell.exe`), 7 ставится отдельно (`pwsh.exe`). Операторы `&&` («выполнить второе, только если первое успешно») и `||` есть только в 7; в 5.1 команда с ними падает с ParserError. Эквивалент в 5.1: `git add -A; if ($?) { git commit -m "..." }`, где `;` разделяет команды, а `$?` хранит успех предыдущей. Проверить версию: `$PSVersionTable.PSVersion`.
- **`$?` и `$LASTEXITCODE`** — автоматические переменные PowerShell: `$?` — успех последней команды (`True`/`False`), `$LASTEXITCODE` — числовой код выхода последней внешней программы (0 = успех у `git`, `flutter`, `dart`).

## Git и GitHub

- **Git** — система контроля версий: хранит историю изменений проекта в скрытой папке `.git` внутри рабочей папки. Каждая зафиксированная точка истории — коммит. Работает полностью локально, сервер не обязателен.
- **Коммит (commit)** — снимок состояния файлов с сообщением «что и зачем изменено». Сначала файлы добавляют в индекс (`git add`), потом фиксируют (`git commit`). У нас сообщения в формате Conventional Commits.
- **`.gitignore`** — список файлов и папок, которые Git не отслеживает: сборка (`build/`), кэш (`.dart_tool/`), ключи подписи (`*.jks`, `*.pfx`). Личные файлы инструментов разработчика (`.idea/`, локальные конфиги ассистентов) тоже туда. `.gitignore` не снимает с учёта файлы, которые уже закоммичены: для них нужен `git rm --cached <путь>` (убирает из индекса, оставляет на диске).
- **GitHub** — хостинг Git-репозиториев. Для нас это резервная копия кода и история, а не сервер приложения: данные пользователя через GitHub не идут, синхронизация устройств остаётся через папку и LAN.
- **Remote / `origin`** — ссылка на удалённую копию репозитория. `origin` — имя по соглашению для основного remote. `git push` отправляет локальные коммиты туда, `git pull` забирает чужие.
- **`git push -u origin main`** — первая отправка ветки с флагом `-u` (upstream): Git запоминает связь локальной `main` с `origin/main`, и дальше достаточно `git push` без аргументов.
- **gh (GitHub CLI)** — консольная утилита GitHub: входит в аккаунт (`gh auth login`), создаёт репозитории (`gh repo create`), открывает PR. Избавляет от кликов в браузере и ручной настройки remote.
- **HTTPS и SSH для Git** — два способа подключения к GitHub. HTTPS проще: `gh auth login` сохраняет токен, и пароль не спрашивается. SSH требует сгенерировать пару ключей и добавить публичный на GitHub; надёжнее для скриптов. Выбираем HTTPS через gh.
- **Публичный репозиторий (public)** — код виден всем, бесплатно даются GitHub Actions, Dependabot, secret scanning, Discussions и Pages. Решили делать публичным; в репозиторий не должны попадать личные данные: ключи подписи, папка синхронизации, реальные задачи.
- **Лицензия MIT** — самая короткая разрешительная лицензия: любой может использовать, менять и распространять код, обязан лишь сохранить уведомление об авторстве; автор ни за что не отвечает. Альтернативы: Apache-2.0 (то же плюс явная защита от патентных претензий, длиннее), GPL-3.0 (производные обязаны открывать код). Файл: LICENSE.
- **Dependabot** — встроенный в GitHub робот: по расписанию проверяет версии зависимостей в `pubspec.yaml` и в самих workflow и открывает PR с обновлением; отдельно присылает оповещения об уязвимостях в зависимостях. Настройка: `.github/dependabot.yml`. Группы (`groups`) собирают связанные пакеты в один PR, иначе build_runner и riverpod_generator обновятся порознь и сломают кодогенерацию.
- **GitHub Actions / CI** — CI (continuous integration, непрерывная интеграция) — автоматический прогон проверок при каждом push и PR на сервере GitHub. Actions — его реализация в GitHub: описание шагов в YAML-файле `.github/workflows/ci.yml`, «раннеры» ubuntu/windows выполняют команды. У нас повторяет чек-лист «Готово» из CONTRIBUTING.md: `build_runner`, `dart format`, `flutter analyze`, тесты, сборка Windows.
- **Action (готовый шаг)** — переиспользуемый блок для workflow из маркетплейса, подключается строкой `uses:`. `actions/checkout` клонирует репозиторий на раннер, `subosito/flutter-action` ставит Flutter SDK нужного канала и кэширует его.
- **Ruleset / branch protection** — правила для ветки `main` в настройках репозитория: запрет push с `--force`, запрет удаления, требование зелёного CI перед слиянием PR. Защищает историю от случайной порчи.
- **Secret scanning и push protection** — GitHub ищет в коммитах похожие на секреты строки (токены API, ключи) и с push protection отклоняет push с ними. Для публичных репозиториев бесплатно и включено по умолчанию.
- **CodeQL** — статический анализ безопасности от GitHub. Dart не поддерживает, поэтому для нас не применим; роль анализатора играет `flutter analyze` в CI.
- **Issue / PR templates** — заготовки форм в `.github/ISSUE_TEMPLATE/*.yml` и `.github/PULL_REQUEST_TEMPLATE.md`: при создании issue или PR поля уже заданы (платформа, пункт TODOIST_PARITY, чек-лист «Готово»).
- **SECURITY.md** — файл с инструкцией, как сообщать об уязвимостях; GitHub показывает его на вкладке Security. Вместе с настройкой «Private vulnerability reporting» даёт приватную форму вместо публичного issue.
- **`.gitattributes` и окончания строк (LF / CRLF)** — Windows заканчивает строки двумя символами CR LF, Linux и Git — одним LF. Без настройки Git на Windows предупреждает «LF will be replaced by CRLF» на каждый файл, а CI на Linux может увидеть «изменённые» файлы. Файл `.gitattributes` в корне задаёт правило `* text=auto eol=lf`: в репозитории и рабочей копии всегда LF, кроме явно перечисленных Windows-файлов (`.ps1`, `.rc`).
- **Fast-forward и «fetch first»** — Git отправляет ветку только если удалённая история — предок локальной. Если на GitHub появился коммит, которого нет у вас (например, README, созданный галочкой на сайте), push отклоняется. Лечится `git pull --rebase`: ваши коммиты переносятся поверх удалённых. Флаг `-X theirs` при rebase решает конфликты в пользу переносимого (вашего) коммита. Контринтуитивно: во время rebase «ours» — это удалённая ветка, «theirs» — ваш коммит.
- **Pull request (PR) и рабочая ветка** — работа над шагом ведётся в отдельной ветке (`git switch -c feat/m1-folder-transport`), ветка отправляется на GitHub, и открывается PR — запрос «влить эту ветку в `main`». CI прогоняет проверки до слияния, а страница PR хранит описание шага и diff. В одиночном проекте PR нужен не для чужого ревью, а как ворота: в `main` попадает только то, что прошло CI. У нас это обязательно: правило required status checks (ruleset) отклоняет прямой `git push` в `main` с ошибкой `GH013`, пока у коммитов нет зелёной проверки `analyze + test`.
- **`git commit --amend`** — заменить последний коммит: добавить забытые файлы или исправить сообщение. Допустимо только пока коммит не отправлен на GitHub, иначе истории расходятся.
- **`.dart_tool/package_config.json`** — файл, который `pub get` создаёт в каждом пакете: таблица «имя пакета → папка с его кодом». Анализатор и компилятор по нему разрешают `import 'package:test/test.dart'`. Пока его нет, любой такой импорт даёт «Target of URI doesn't exist». Поэтому в CI `dart pub get` для `packages/oplog_sync` стоит до `flutter analyze`: анализ из корня проверяет и вложенные пакеты.
- **Native assets / build-хуки (`hook/build.dart`)** — новый механизм Dart: пакет может содержать скрипт, который при `flutter run`, `flutter test` или сборке компилирует свой C-код под текущую платформу. У нас так работает `cnativeapi` (через `tray_manager` → `nativeapi`). Побочный эффект: даже widget-тесты требуют компилятор и системные заголовки, на Linux это GTK 3, X11 и Xi.
- **pkg-config** — утилита Linux, по которой компилятор узнаёт флаги и пути системных библиотек (`pkg-config --cflags gtk+-3.0`). Сообщение «Package gtk+-3.0 was not found» значит, что не установлен dev-пакет с заголовками: `libgtk-3-dev`.
- **apt-get в CI** — раннер `ubuntu-latest` даёт чистую Ubuntu, недостающие системные пакеты ставим шагом `sudo apt-get install` до запуска Flutter. Флаг `--no-install-recommends` не тянет необязательные зависимости и экономит время.
- **Бейдж (badge)** — картинка-статус в README, например «CI passing». Адрес вида `https://github.com/ЛОГИН/planner/actions/workflows/ci.yml/badge.svg`.

## Этап M0 — создание проекта

- **pubspec.yaml / pub.dev** — манифест Dart-проекта: имя, версия, список зависимостей с диапазонами версий (`^2.35.2` = «2.35.2 и выше, но ниже 3.0»). pub.dev — официальный каталог пакетов. `flutter pub get` скачивает зависимости и фиксирует точные версии в `pubspec.lock`.
- **Разрешение версий (version solving)** — pub подбирает версии всех пакетов так, чтобы их взаимные ограничения не противоречили. Конфликт (как у нас `build_runner` 2.17 и `riverpod_generator`) лечится откатом одного пакета на ветку, которую поддерживают оба.
- **Монорепозиторий, path-зависимость** — `oplog_sync: path: packages/oplog_sync` подключает наш пакет из соседней папки, а не из pub.dev.
- **analysis_options.yaml** — настройки статического анализа: набор правил (`flutter_lints`), строгость типов (`strict-casts`, `strict-inference`, `strict-raw-types` — запрет неявных приведений и «угадывания» типов) и исключения для сгенерированных файлов.
- **Плагин анализатора (`plugins:` верхнего уровня)** — новая система Dart 3.10+: пакет-линтер (`riverpod_lint`) подключается прямо в analysis_options.yaml, без `custom_lint` и без записи в pubspec. Правила плагина видит и IDE, и `flutter analyze`.
- **`flutter create --org dev.local`** — генератор каркаса; `--org` задаёт обратное доменное имя, из которого собирается идентификатор приложения `dev.local.planner` (так Android и Windows различают программы).
- **Режим разработчика Windows (Developer Mode)** — системная настройка, разрешающая создавать символические ссылки без прав администратора. Flutter-плагины подключаются к сборке именно через них, поэтому без режима `flutter build windows` отказывает.
- **Символическая ссылка (symlink)** — файл-указатель на другой файл или папку; ОС прозрачно подставляет оригинал.
- **`sealed class` + `switch`** — закрытая иерархия: все наследники известны компилятору (`Result` = `Ok | Err`), и `switch` обязан разобрать каждый случай, иначе ошибка компиляции. Так нельзя забыть обработать ошибку. Файл: lib/core/result.dart.
- **`abstract interface class`** — чистый интерфейс без реализации: класс можно только `implements`. Так объявлены `OpStore`, `SyncFs`, `AppClock`, чтобы тесты подставляли фейки.
- **`final class`** — класс, от которого нельзя наследоваться вне его библиотеки; защищает инварианты `Hlc`, `Op`, `MergeEngine`.
- **Инжекция зависимостей (DI)** — объект получает «часы», «генератор ID» и хранилище через конструктор, а не создаёт сам. В тестах вместо них передаются управляемые заглушки (`FixedClock`, счётчик вместо UUID).
- **ProviderScope / ConsumerWidget** — корень Riverpod и виджет, который умеет читать провайдеры через `ref.watch`. `routerProvider` создаёт `GoRouter` один раз (`keepAlive: true`).
- **`MaterialApp.router`** — вариант корневого виджета Flutter, который отдаёт навигацию внешнему роутеру (go_router) вместо встроенного `Navigator`.
- **`part` / `part of`** — файл-«часть» той же библиотеки: `router.g.dart`, который генерирует build_runner, видит приватные члены `router.dart`.
- **Unix-миллисекунды** — число миллисекунд с 1 января 1970 UTC; так хранятся время в `Hlc.wallMs` и первые 48 бит UUIDv7.
- **RFC 9562** — стандарт форматов UUID, включая версию 7. Версия и вариант закодированы фиксированными битами, поэтому любой инструмент распознаёт наш ID.
- **Правило Кулкарни (HLC receive)** — формула обновления гибридных часов при получении чужой метки: берём максимум из трёх времён (своё, своих часов, чужое) и так растим счётчик, чтобы новая метка была строго больше и своей, и чужой. Файл: packages/oplog_sync/lib/src/hlc.dart.
- **NDJSON-чанк** — файл журнала `000001.ndjson` с ops узла, по одной на строку. Каждая выгрузка пишет новый чанк целиком, после записи он не меняется (неизменяемый). Последняя строка — `{"end": N}` («завершающая строка», trailer): по ней читатель понимает, что файл дошёл целиком. Файл: packages/oplog_sync/lib/src/folder_transport.dart.
- **Id папки (`folder_id`)** — случайный идентификатор в `format.json`, созданный вместе с папкой синхронизации. Устройство помнит, к какой папке относятся его курсоры; если id другой (папку сменили или пересоздали), курсоры сбрасываются, и всё читается и выгружается заново.
- **Smoke-тест** — минимальная проверка «приложение запускается и показывает главный экран» без деталей; ловит сломанную сборку или DI. Файл: test/app/app_test.dart.
- **Детерминированность слияния** — результат зависит только от самих данных (операций и их меток), а не от порядка прихода или устройства, на котором считали. Поэтому ничья при равных `wallMs` и `counter` решается по `nodeId`: обе стороны видят одно и то же и приходят к одному ответу. «Кто пришёл первым» на разных устройствах разный и развёл бы копии навсегда.
- **Параллельная (concurrent) правка** — два устройства изменили одно поле, и ни одно не видело правку другого. Противоположность последовательной правке, когда второе устройство уже получило первую и сознательно её заменило. Только параллельная правка — конфликт, который показываем пользователю.
- **`base` в Op** — что автор знал о сущности перед правкой: самая поздняя метка HLC среди ops этой сущности, пришедших к нему с других устройств. По ней получатель понимает, видел ли автор чужую правку: если `base` меньше её метки — не видел, и правки параллельные. Простой способ отследить причинность без векторных часов.
- **Причинность (causality)** — отношение «событие Б произошло, зная о событии А». Синхронизация без сервера обязана её учитывать: иначе нельзя отличить осознанную замену от случайного затирания.
- **Детерминированный id** — идентификатор, вычисленный из самих данных (хеш sha256 от entity_id, поля и двух меток), а не случайный. Два устройства, обнаружив один конфликт, получают одну и ту же запись `conflict`, и дубликатов не возникает.
- **Хеш-функция, SHA-256** — функция, превращающая любые данные в «отпечаток» фиксированной длины (у SHA-256 — 32 байта). Одинаковый вход всегда даёт одинаковый отпечаток, а подобрать другой вход с тем же отпечатком практически невозможно. Нам нужна для детерминированных id; берём из официального пакета `crypto`, а не пишем сами. Файл: packages/oplog_sync/lib/src/conflict.dart.
- **UUIDv8** — версия UUID из RFC 9562 «по своему алгоритму»: формат стандартный (версия и вариант в фиксированных битах), содержимое выбирает приложение. У нас это первые 16 байт SHA-256, поэтому id конфликта выглядит как обычный UUID.
- **Чистая функция** — функция, результат которой зависит только от аргументов и которая ничего не меняет вокруг (не пишет в базу, не смотрит на часы). `findConflicts` — чистая: на одних ops всегда даёт одни конфликты, поэтому её легко тестировать и ей можно доверить детерминированность.
- **Производная запись** — данные, которые не хранятся как первоисточник, а вычисляются из других (как проекции из журнала). Запись конфликта производная: её можно стереть и пересчитать из ops, и синхронизировать её не нужно — каждое устройство посчитает сам. Синхронизируется только решение пользователя (`resolved`).
- **Атомарная запись (temp + rename)** — файл сначала пишется под временным именем, потом одним действием переименовывается в настоящее. Переименование в пределах папки операционная система делает «всё или ничего», поэтому другая программа (облачный клиент) никогда не увидит полузаписанный файл под настоящим именем. Обязанность реализации `SyncFs.writeString`.
- **Курсор синхронизации** — закладка «до какого чанка этого устройства мы уже дочитали». Хранится у каждого устройства своя (`SyncStateStore`, в приложении — таблица `sync_cursors`) и сдвигается только после того, как чанк применён целиком. Если что-то пошло не так, курсор стоит, и чанк перечитывается в следующий раз.
- **Водяной знак (watermark)** — граница «всё до этой отметки уже обработано». У нас — HLC последней своей op, уже записанной в папку: при следующей выгрузке берём только свои ops с HLC больше него. Работает, потому что HLC своих ops строго растёт.
- **Недокачанный файл** — облачный клиент (OneDrive, Google Drive) скачивает файлы с задержкой и не в порядке создания: чанк 2 может появиться раньше чанка 1, а файл — оказаться обрезанным на середине. Поэтому читатель проверяет `\n` в конце файла и непрерывность номеров и при сомнении просто ждёт следующей синхронизации.
- **Мутационная проверка тестов** — намеренно сломать код (например, убрать проверку пропуска номера) и убедиться, что тест падает. Если не падает — тест ничего не проверяет. Так проверены тесты `FolderTransport`.
