# План M1 — ядро синхронизации

Цель этапа (docs/ROADMAP.md): два узла сходятся во всех сценариях пакета и test/sync;
конфликт создаётся на обоих узлах с одним id. Интерфейса в M1 нет — только ядро, база и тесты.

Исходное состояние (M0): `Hlc`, `Op` без `base`, `MergeEngine` (LWW, дедупликация, отклонение
op из будущего, `rebuild`), `MemoryOpStore`, интерфейс `SyncFs` + `MemorySyncFs`,
`FolderTransport` — заглушка. В приложении drift подключён, но таблиц нет.

## Шаги (каждый — отдельный коммит)

### M1.1 — `base` и детекция конфликтов (пакет) — готово 23.10.2026
- `Op.base: Hlc?` — что автор знал о сущности: макс. HLC ops этой сущности от *других* узлов в его
  журнале (общий для всех полей одной правки); в JSON ключ `base`. Формат v1 ещё нигде не записан,
  поэтому версия не меняется.
- Детекция — **попарная чистая функция от набора ops** (`findConflicts`), не от порядка прихода.
  Пара ops с разных узлов параллельна, если ни один автор не видел другую (`base < чужой hlc`).
  Параллельная пара на одно поле с разными значениями — `edit`; tombstone + правка обычного поля —
  `delete`. Проверяется и при приёме, и при локальной правке — одинаково на всех узлах.
- Первый вариант (`base` = HLC значения поля + поиск op воскрешения для `delete`) ревью отклонило:
  ложные конфликты после «Отменить» удаление и зависимость от порядка ops внутри пакета
  (инкрементальный результат ≠ rebuild). Попарный критерий с `base` на уровне сущности снимает оба.
- Id конфликта детерминирован: `sha256(entity_id, kind, field, min(hlc), max(hlc))` → оба узла
  получают одну запись. `kind` в хеше: правка может спорить одновременно с правкой поля и с
  удалением, записанными одной группой с общим HLC.
- **Конфликт — производная запись, а не ops.** Строка конфликта вычисляется из журнала (как
  проекция) и пересоздаётся `rebuild`. Через op синхронизируется только `resolved=true`.
  Альтернатива «создавать конфликт ops-ами» отвергнута: узел B, позже заметивший конфликт, записал бы
  `resolved=false` с более свежим HLC, чем уже сделанный на A выбор, и конфликт бы «воскрес».
- `OpStore` получает: `opsForEntity(...)` (для детекции и `base`), `putConflict(...)`, `conflicts()`.
  `ApplyReport.conflicts` — новые и ещё не разрешённые к концу пакета.
- На M2 (экран и уведомления): группировать конфликты одного поля/сущности в одно уведомление
  (N параллельных правок дают N пар); конфликт `delete`, когда удаление уже отменено, показывать
  как неактуальный; конфликты от локальной правки уже удалённой задачи брать из таблицы, а не из отчёта.
- Точность: для двух устройств правило точное. Для трёх и более возможен редкий пропуск
  уведомления — **на сходимость данных это не влияет**: LWW работает независимо от детекции.
- Тесты: параллельная правка одного поля → конфликт с одним id на обоих узлах; последовательная —
  нет; одинаковые значения — нет; разные поля — нет; правка vs удаление; разрешение на одном узле
  закрывает на другом; порядок доставки и повторная доставка не меняют набор конфликтов; `rebuild`
  восстанавливает конфликты и их `resolved`.

### M1.2 — `FolderTransport` (пакет, на `MemorySyncFs`) — готово 23.10.2026
Сверх плана: узел читает и свою папку (после восстановления из копии возвращаются свои ops);
пропуск номера чанка — ждать, а не перескакивать; «выгружено до» — HLC-водяной знак +
`OpStore.opsOfNodeAfter`; `Hlc.parse` проверяет диапазоны. SYNC_DESIGN «Транспорт A» обновлён.
По ревью: правка не делится между чанками; строка `{"end": N}` в конце чанка; `folder_id` в
`format.json` и сброс курсоров при смене папки; нечитаемый файл — `ChunkIssue.io`, а не остановка;
проверка «часы движка ≥ водяного знака».

- Раскладка по SYNC_DESIGN: `format.json`, `nodes/<node>/info.json`, чанки `<seq>.ndjson`.
- Выгрузка: свои ops, ещё не выгруженные, пишутся новым неизменяемым чанком (temp + rename,
  `writeString`); чанк > ~1 МБ делится. Номер следующего чанка = max(существующих) + 1 — существующий
  файл никогда не перезаписывается (защита при восстановлении базы из бэкапа).
- Чтение: для каждого чужого узла — чанки с `seq` > курсора по порядку; неполная последняя строка или
  битая строка → чанк пропускается до следующего раза, курсор не двигается; если в чанке есть
  `rejected` (часы автора ушли вперёд) — курсор тоже не двигается, чанк перечитается позже.
- `format.json` с `v` больше поддерживаемого → синхронизация останавливается с понятной ошибкой.
- Курсоры и «выгружено до» — новый интерфейс `SyncStateStore` (в пакете `MemorySyncStateStore`,
  в приложении — таблица `sync_cursors`).
- Тесты: два и три узла через одну `MemorySyncFs`, все сценарии из «Инвариантов реализации»;
  частично записанный файл; битая строка; чужая версия формата; восстановление из бэкапа не
  затирает чанки.

### M1.3 — схема drift и `DriftOpStore` (приложение) — детальный план: docs/plans/m1-3-drift-store.md
- Таблицы: `ops` (журнал, индекс по entity_type+entity_id+field), `field_versions`
  (HLC каждого поля проекции), `conflicts`, `sync_cursors`, `local_meta` (node_id, состояние HLC —
  локальное, не синхронизируется), проекции `projects` и `tasks` с базовыми полями.
  Остальные сущности (разделы, метки, …) добавляются в M2 миграциями — заодно проверим механизм миграций.
- `DriftOpStore implements OpStore`: запись поля в проекцию через реестр «тип сущности → проектор»
  (имена колонок из белого списка, не из данных).
- Автобэкап файла БД перед миграцией (`backups/`, хранить 14) — закладываем сейчас, пока схема v1.
- Тесты на in-memory drift: тот же набор, что у `MemoryOpStore` (общий контрактный тест),
  `rebuildFromOps` даёт ту же базу, что инкрементальное применение.

### M1.4 — `Mutator`, адаптер ФС Windows, двухузловые сценарии (приложение)
- `lib/sync/mutator.dart`: create / update / delete поверх `MergeEngine`, id из `IdGenerator`,
  время из `AppClock`; Riverpod-провайдеры для базы, движка и `Mutator`. Состояние HLC сохраняется в `local_meta`.
- `lib/sync/io_sync_fs.dart`: `SyncFs` на `dart:io` (Windows): атомарная запись temp + rename.
- test/sync: два узла (две in-memory базы) через временную папку на диске и `FolderTransport` —
  полный список сценариев из инвариантов, включая «оба завершили повторяющуюся» на уровне ops.
- Цикл синхронизации по таймеру и выбор папки — в M2 вместе с экраном настроек.
- Из ревью M1.2 (обязательно здесь):
  - Часы движка при запуске = max(сохранённые в `local_meta`, макс. HLC своих ops в журнале) —
    иначе `FolderTransport` откажется выгружать (водяной знак).
  - Один `MergeEngine` + один `FolderTransport` на базу: на Android фоновая задача и UI не должны
    синхронизировать одновременно — межпроцессная блокировка (lock-файл или блокировка БД).
  - `IoSyncFs.writeString` чанка — «создать, только если файла нет»; при конфликте брать следующий номер.
- Известные ограничения (не теряют данные, вернуться в M2/M12):
  - После восстановления из копии свои ops из своей папки выгружаются повторно (папка растёт).
  - Копии облачного клиента «000005 (1).ndjson» не читаются; совпадение номеров возможно, только если
    базу восстановили на другом ПК до скачивания своих чанков. Тогда — читать копии как неупорядоченный вход.
  - Сбой между `applyAll` и сдвигом курсора: конфликт останется в таблице, но уведомления о нём не будет.

## Принятые решения (23.10.2026)
1. Хеш для детерминированных id — `package:crypto` (официальный пакет Dart, без Flutter).
   Альтернативы: свой SHA-256 (лишний риск ошибки в криптокоде), склейка op_id без хеша (длинные id).
2. Чанки — новый неизменяемый файл на каждую выгрузку. Альтернатива: перезапись открытого чанка
   до 1 МБ (меньше файлов, но облако чаще видит меняющийся файл, а читателю нужен курсор «файл + строка»).
3. Снапшоты — в M12 вместе с компакцией; в M1 новое устройство читает все чанки.
