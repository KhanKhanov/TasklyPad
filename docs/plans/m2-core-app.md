# План M2 — вести дела на Windows

Черновик 24.10.2026, ждёт утверждения. Этап M2 из docs/ROADMAP.md: «Входящие», проекты, разделы, задачи,
подзадачи, метки, приоритеты, панель задачи, список (TODOIST_PARITY §1, §3 частично), экран «Конфликты»
и уведомление (§9), плюс обязательства из ревью M1.4 (docs/plans/m1-4-mutator-sync.md, «Обязательно в M2»):
один экземпляр на Windows, смена папки синхронизации, проверка на настоящем OneDrive. Сюда же из M1.4
переехали таймер синхронизации и выбор папки.

**Готово, когда:** на Windows можно вести дела каждый день: проекты, разделы, задачи с подзадачами,
сроками, приоритетами и метками; два экземпляра (два профиля) сходятся через папку OneDrive; конфликт
виден в уведомлении и на экране «Конфликты» и закрывается выбором.

## Шаги: три PR
Меньше трёх не получается без потери проверяемости: шаг 1 впервые меняет схему базы (первая миграция,
данные пользователя), его надо ревьюить отдельно от ~3000 строк интерфейса. Больше трёх не нужно: внутри
каждого шага коммиты независимы и проверяются тестами одним прогоном.

| Шаг | Ветка | Что | Зависит от |
|---|---|---|---|
| M2.1 | `feat/m2-1-data-model` | Схема v2, команды и чтение без UI, двухузловые тесты | main |
| M2.2 | `feat/m2-2-ui` | Оболочка, сайдбар, список, панель задачи, метки, отмена, хоткеи | M2.1 |
| M2.3 | `feat/m2-3-sync-app` | Один экземпляр, профили, настройки синхронизации, смена папки, «Конфликты» | M2.2 |

Параллельно можно вести только коммит «один экземпляр» из M2.3 (трогает лишь `windows/runner`), но выигрыш
мал — по умолчанию шаги идут подряд.

## Ключевые решения
1. **Метки задачи — отдельная сущность `task_label`** {task_id, label_id, deleted} с детерминированным
   id = UUIDv8(sha256("task_label", task_id, label_id)). Два устройства, поставившие одну метку офлайн,
   пишут одну и ту же сущность — одинаковые значения, не конфликт; снятие метки = tombstone.
   Альтернатива: поле-список `labels` у задачи, как в API Todoist, — LWW на весь список теряет
   параллельные добавления (A добавил @дом, B — @срочно: остаётся одно, плюс конфликт).
   Для id — общая функция `uuidV8(parts)` в пакете (её же использует `conflictId`).
2. **Каскад — вычисляемый, а не ops-ами.** Удаление (и архив) проекта, раздела или родительской задачи —
   одна op на самой сущности. Потомки скрываются запросом: элемент жив, если жив он и вся цепочка
   предков (проект → раздел → родитель). «Отменить» = одна op `deleted=false`, и потомки возвращаются.
   Альтернатива: tombstone каждому потомку — N ops; подзадача, добавленная офлайн на другом устройстве,
   осталась бы сиротой; отмена должна восстановить ровно тех, кого удалили, а не удалённых раньше.
   Физически строки уйдут только компакцией (M12).
3. **Дерево строится при чтении, с защитой от циклов.** Параллельные переносы (A: X под Y, B: Y под X)
   дают цикл `parent_id`. Чтение разрывает его детерминированно: в цикле корнем становится элемент с
   наименьшим id — на всех устройствах одинаково. Глубина (подзадачи — 4 уровня, подпроекты — 3, до 20
   разделов в проекте — по help Todoist) ограничивается только при записи в UI; пришедшее с другого
   устройства глубже — показывается как есть.
4. **У подзадачи свой `project_id`/`section_id`** (как в Todoist API — нужно фильтрам M5 и CSV M11).
   Перенос задачи пишет проект и раздел всему поддереву одной транзакцией. Показ — по дереву `parent_id`:
   если после параллельных правок проект подзадачи разошёлся с родителем, она всё равно видна под ним.
5. **`Mutator.batch`** — несколько правок разных сущностей одной транзакцией (задача + её метки, перенос
   поддерева, завершение с подзадачами). Ops одного действия пользователя атомарны: синхронизация видит
   либо все, либо ни одной.
6. **«Отменить» = обратные ops.** Перед действием читаем текущие значения затронутых полей
   (`field_versions`), по кнопке в тосте пишем их обратно новыми ops. Удалять ops из журнала нельзя:
   они могли уже уйти в папку. Если за время тоста поле изменило другое устройство, отмена — обычная правка
   поверх. Тост — для завершения и переноса; **удаление — с подтверждением и без тоста**, как в Todoist
   («There's no option to undo task deletion»). Данные при этом не теряются: удаление — tombstone, вернуть
   можно будет из журнала активности (M8). Длительность тоста в help не указана — берём 5 с как допущение.
7. **Чтение — репозитории со стримами drift → freezed-модели домена** (`Task`, `Project`, `Section`,
   `Label`). UI не видит типов drift и получает готовые производные: дерево, «жив ли», счётчики.
   Альтернатива: строки drift прямо в UI — меньше кода, но UI зависит от схемы, а дерево и каскад
   пришлось бы считать в виджетах.
8. **Свёрнутость** раздела, задачи с подзадачами и проекта в сайдбаре — синхронизируемые поля
   `is_collapsed` (в Todoist они общие для устройств). Добавляются в `silentFields`: спорить о них незачем.
9. **Схема v2 одной миграцией** — сразу все колонки M2, включая `deadline` и `duration` задачи (они в
   панели задачи Todoist; без них пришлось бы мигрировать ещё раз). Миграция через
   `drift_dev make-migrations`: снимки схем v1/v2 в репозитории и сгенерированный тест перехода.
10. **Синхронизация в приложении:** проход по таймеру (60 с), через 5 с после локальной правки (debounce),
    при возврате фокуса окну и кнопкой «Синхронизировать». Пока окно закрыто — нет (трей — M9).
    Альтернатива: слежение за файлами папки — уведомления OneDrive о чужих файлах ненадёжны; решить в M6 (О-13).
11. **Папка** выбирается системным диалогом (`file_selector`, официальный пакет Flutter); путь хранится в
    `local_meta` (`sync.folder_path`) — локально, не синхронизируется (SYNC_DESIGN «Специальные случаи»).
12. **Смена папки = переиздание правок устройств, отмеченных «больше не используется»** (решение
    пользователя 27.10.2026). Диалог смены папки показывает другие устройства прежней папки (из их
    `info.json`), по умолчанию не отмеченные. Если отмечен хоть один, сначала — последний проход с прежней
    папкой: переиздаётся только то, что уже в журнале, а выбывшее устройство могло выгрузить правки после
    нашего прошлого прохода (дополнение по ревью, подтверждено пользователем 27.10.2026). Чанк отмеченного
    узла не прочитан (любой вид ошибки) или прежняя папка недоступна целиком (удалена, не читается,
    записана более новой версией; пропавшую папку проход не создаёт заново — SYNC_DESIGN «Транспорт A») — смена не начинается, и
    приложение спрашивает: подождать или «Сменить всё равно». Отказ — под статусом «попробуйте позже» (до
    следующего прохода); «всё равно» — переиздаётся прочитанное, а
    тост (10 с) предупреждает, у скольких устройств прочитано не всё и что непрочитанное осталось в
    прежней папке (решение пользователя 27.10.2026). Причина: по виду ошибки не понять, пройдёт ли она
    сама — запись чанка атомарна, поэтому обрезанный или нечитаемый файл одинаков и при докачке, и при
    порче, а отклонённые ops (часы узла впереди больше `Hlc.maxDrift`, 1 ч) принимаются, когда наши часы
    догонят. Отклонены: делить ошибки по виду на «временные» и «постоянные» — устойчивая порча
    блокировала бы смену навсегда, а спешащие на пару часов часы теряли бы правки без нужды; считать
    ошибку постоянной через сутки — ждать сутки при порче и отметка времени ради редкого случая; всегда
    «попробуйте позже» — смена может не пройти никогда; снять отметку — не перенесётся и прочитанное.
    Сбой первого прохода с новой папкой смену не отменяет: папка и копии уже
    сохранены, ошибка — под статусом, тост с итогом переиздания показывается. Правки узла применяются строго по порядку (SYNC_DESIGN «Транспорт A»), поэтому после непрочитанного
    чанка не переиздаются и целые чанки за ним. Последний чанк, которого облако ещё не
    создало, проход не замечает: пропуск виден только в середине номеров. Затем, перед первым проходом с новой папкой, для каждого отмеченного
    узла вызывается уже существующий `MergeEngine.adopt(node, null)` — его побеждающие ops переиздаются от
    нас с исходным временем и уходят в новую папку первым же проходом (другая папка сбрасывает водяной
    знак выгрузки). Не после прохода: копии сохраняют исходное время, и водяной знак, уже сдвинутый своими
    новыми правками, остался бы впереди них — копии не выгрузились бы никогда (найдено тестом,
    test/sync/sync_runner_test.dart). Живые устройства не отмечают: они переключатся на новую папку и
    выгрузят свой журнал сами. Переиздавать всех, кого нет в новой папке (первый вариант), нельзя: если
    такое устройство живо и успеет поправить поле до переезда, копия и его правка расходятся по `base`, и
    на всех устройствах возникает ложный конфликт (проверено тестом двух узлов); кроме того, устройство с
    устаревшей папкой в новой папке «присутствует», и его поздние правки не переиздавались бы. Отклонены:
    поле исходного автора в каждой op — новая версия формата ops и миграция ради незаметности; только
    предупреждение — новые устройства не увидят правок выбывших; копировать чужие папки узлов в новую —
    нарушает «узел пишет только в свою папку». Ошибочно отмеченное живое устройство даёт тот же ложный
    конфликт — он виден и решается на экране «Конфликты». Ограничение (принято пользователем 27.10.2026;
    отклонено — показывать и узлы из журнала: давно выбывшие предлагались бы при каждой смене, а повторная
    отметка повторяет копии, О-31): в списке только устройства прежней
    папки. Устройство, которое не отметили и которое так и не переехало, в следующей папке уже не
    предлагается; его правки, известные этому устройству, туда не попадут.
13. **Один экземпляр на Windows** — именованный mutex в `windows/runner/main.cpp`; второй запуск находит
    окно первого, показывает его и выходит (как Todoist). Альтернатива: Dart-пакет single instance через
    именованные каналы — лишняя зависимость ради ~25 строк C++. Водяной знак по `rowid` не делаем: mutex
    закрывает Windows, на Android процесс один (О-11).
14. **Профили для ручной проверки:** `--profile <имя>` — своя папка данных, своя метка узла и своё имя
    mutex. Так на одном ПК живут два «устройства» и синхронизируются через одну папку OneDrive — до
    Android (M6) это единственная ручная проверка двух узлов.
15. **Уведомление о конфликте** — интерфейс `ConflictNotifier` в lib/platform, реализация на
    `flutter_local_notifications` (toast Windows), фейк в тестах. Клик ведёт на `/conflicts`. Значения
    сторон берутся из ops (`older_op_id`, `newer_op_id`) и показываются по типу поля (приоритет — «Приоритет 2»,
    срок — дата, проект — имя).

### Итог M2.1 (24.10.2026)
- Приложение: 305 тестов (+73), пакет: 151 (+4), integration_test на Windows: 2. Мутационная проверка: без
  `is_collapsed` в `silentFields`, без каскада удаления проекта, со случайным id связи метки, без транзакции
  миграции, с записью неизменённых полей, без проекта из раздела, без перевыдачи совпавших ключей — падает
  свой тест.
- По ревью:
  - **решение 4 изменено**: проект подзадачи и корневой задачи в живом разделе вычисляются (корень, раздел),
    перенос задачи и раздела пишет поля только самой сущности. Иначе перенос родителя спорил с удалением
    подзадачи на другом устройстве (ложный конфликт удаления), а задача, добавленная в раздел, который
    параллельно перенесли в другой проект, была жива, но не видна ни в одном списке;
  - `Mutator.update` пишет только изменённые поля — перестановка задачи больше не откатывает перенос её
    подзадачи на другом устройстве, снятие метки даёт один конфликт, а не три;
  - ключи порядка: `keyForInsert` (вставка по позиции, равные ключи соседей учтены) и `rekeyInOrder`
    (при совпавших ключах перевыдаёт минимум ключей) вместо `keyBetween`;
  - раздел чужого проекта при добавлении задачи отклоняется; дубликат проекта — у действующего родителя.
- Отклонения от черновика:
  - **миграция в транзакции** (сверх плана): drift сам транзакцию не открывает и пишет `user_version` после
    шагов — оборванная миграция ломала бы следующий запуск на «duplicate column»; шаги и `user_version`
    теперь в одной транзакции, тест со сбоем посередине;
  - решение 7 уточнено: вместо репозитория на каждый экран — **один снимок `Workspace`**, все представления —
    чистые функции от него (тестируются без базы);
  - `deadline` и `duration` — поля-объекты, как в Todoist API ({date}, {amount, unit}): параллельная правка —
    один конфликт;
  - завершение родителя пишет явные ops каждой незавершённой подзадаче (у каждой своя дата завершения),
    а удаление и архив — вычисляемые; отмена завершения подзадачи возвращает предков;
  - запрет пробелов в имени метки снят — в help не подтверждён; имя уникально без учёта регистра;
  - уровни вложенности считаются как `INDENT` CSV Todoist (1 — верхний): задачи до 4, проекты до 3.
- Провайдеры Riverpod для действий и снимка — в M2.2 вместе с экранами.

## M2.2 — интерфейс
До экранов: О-4 (интерфейс Todoist) — ответы записываются сюда же, в «Сверка с Todoist».
Коммиты:
0. `fix(tasks): возврат задачи, архив раздела и проекта как в Todoist` — `uncomplete` восстанавливает
   архивный раздел корневой задачи и ставит возвращённые задачи в конец списка родителя; архив раздела
   завершает его задачи (после возврата раздела они остаются завершёнными); `unarchive` проекта с
   архивным предком делает его корневым в конце списка; `Mutator.update` не пишет значение по умолчанию
   в поле, которого ещё нет. Тесты, в том числе на двух устройствах.

2. `feat(tasks): список задач, подзадачи и панель задачи` — строка задачи (кружок цвета приоритета, срок,

  сохранённая папка; непрочитанный чанк выбывшего устройства — вопрос «подождать или сменить всё равно».
- Коммит 1 — сделан. Mutex `Local\planner.instance` (у профиля —
  `Local\planner.instance.p.<имя>`) в windows/runner/main.cpp; второй запуск находит окно первого по
  классу окна Flutter и заголовку («planner», у профиля — «planner — <имя>»), разворачивает его и выходит
  с кодом 0. Если окна нет (прежний экземпляр закрывается), второй ждёт освобождения замка до 10 с и
  работает как первый; если замок проверить нельзя — не запускается: сохранность данных важнее. Профиль:
  `--profile <имя>` или `--profile=<имя>`, имя — латинские строчные буквы, цифры и дефис, до 32 символов,
  не имя устройства Windows (часть пути и имени mutex); неверное имя — экран ошибки запуска, mutex не
  берётся. Папки профиля — `profiles/<имя>` внутри папки базы и папки метки узла; у основного профиля
  пути прежние. Запуск второго «устройства» при разработке:
  `flutter run -d windows --dart-entrypoint-args=--profile=b`. Пока открыто приложение основного
  профиля, `flutter run` и integration-тесты без профиля не запустятся — второй запуск покажет его окно
  и выйдет. Окно ищется по заголовку — до трея (M9) этого хватает; скрытое в трей окно и смена заголовка —
  О-29.

Ручная проверка (финал M2): два профиля на одном ПК через папку OneDrive — правки сходятся, параллельная
правка одного поля даёт конфликт на обоих, выбор на одном закрывает на другом; второй запуск того же
профиля показывает окно первого; временные файлы `IoSyncFs` не остаются в папке OneDrive.

## Сверка с Todoist
Подтверждено официальной документацией API v1 (developer.todoist.com/api/v1, разделы Tasks, Projects,
Sections, Labels) и официальным SDK (github.com/Doist/todoist-sdk-typescript, `src/utils/colors.ts`):
- завершение задачи завершает её подзадачи («Completes a task and its sub-tasks»); удаление задачи
  удаляет подзадачи; удаление и архив раздела — вместе с его задачами; удаление и архив проекта — вместе
  с потомками. В M2.1 так и сделано;
- возврат задачи в работу восстанавливает завершённых предков **и разделы**, а восстановленные задачи
  встают **в конец** списка своего родителя. В M2.1 разделы не восстанавливаются и место не меняется —
  исправление в M2.2;
- разархивирование проекта не трогает предков: если родитель в архиве, проект становится корневым и
  встаёт в конец корневых. В M2.1 этого нет — исправление в M2.2;
- удаление метки снимает её с задач (API). По help «Introduction to labels» — только с активных: на
  выполненных она остаётся, а возврат такой задачи в работу создаёт метку заново с тем же именем. В
  M2.1 метка скрывалась со всех задач — исправлено в M2.3, пункт 5;
- палитра — 20 цветов, по умолчанию `charcoal`; hex — из SDK: berry_red #b8255f, red #db4035,
  orange #ff9933, yellow #fad000, olive_green #afb83b, lime_green #7ecc49, green #299438,
  mint_green #6accbc, teal #158fad, sky_blue #14aaf5, light_blue #96c3eb, blue #4073ff, grape #884dff,
  violet #af38eb, lavender #eb96eb, magenta #e05194, salmon #ff8d85, charcoal #808080, grey #b8b8b8,
  taupe #ccac93.

Интерфейс — по help Todoist (официально, если не помечено иначе):

  подзадачи — родитель), название со стрелками «предыдущая / следующая задача», описание, «Подзадачи»
  (прогресс, счётчик, «Показать / скрыть выполненные»), «Комментарии»; справа сверху вниз — Проект,
