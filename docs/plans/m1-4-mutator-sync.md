# План M1.4 — `Mutator`, `IoSyncFs`, запуск и двухузловые сценарии

Часть этапа M1 (docs/plans/m1-sync-core.md, раздел M1.4). Интерфейса нет: ядро, база, адаптеры, тесты.
Цикл синхронизации по таймеру и выбор папки — в M2 вместе с экраном настроек.

## Ключевые решения
1. **`SyncFs.writeStringIfAbsent`** — новый метод интерфейса пакета: записать файл атомарно, только если
   его нет (`false` — файл уже есть и не тронут). Через него пишутся чанки (занят номер → следующий) и
   `format.json` (два устройства создают папку одновременно → второе читает id первого, а не затирает).
   Альтернатива: проверка `exists` в транспорте перед `writeString` — окно между проверкой и записью у
   транспорта шире, а в памяти (`MemorySyncFs`) метод точный.
2. **`IoSyncFs`** (`dart:io`): временный файл `.<имя>.<pid>-<n>.tmp` в той же папке → `rename`.
   `writeStringIfAbsent` проверяет файл до записи и перед `rename`; узкое окно между проверкой и
   `rename` остаётся (в `dart:io` нет «переименовать без замены»). Гарантию «один писатель в папку узла»
   даёт аренда синхронизации (п. 3) и уникальный `node_id` (п. 4), проверка — вторая линия защиты.
   Альтернатива: `File.create(exclusive: true)` + дозапись — после сбоя на середине остаётся
   недописанный чанк, на котором читатели остановятся навсегда.
3. **Аренда синхронизации (lease) в базе** — строка `sync.lease` в `local_meta` `{owner, until_ms}`,
   захват одним условным UPSERT (атомарно для всех соединений SQLite), срок 10 минут, после
   синхронизации освобождается. Кто не захватил — пропускает цикл.
   Альтернативы: lock-файл через `RandomAccessFile.lock` — на Android это `fcntl`-блокировка, она
   действует между процессами, но не между изолятами одного процесса (фоновая задача и UI могут быть
   в одном); эксклюзивная транзакция SQLite на всю синхронизацию — блокирует запись из UI.
4. **Опознание копии базы** — `node_id` хранится в базе и в файле-метке вне базы (`node_id.txt`):
   Windows — Local AppData (не копируется вместе с Roaming и папкой программы), Android —
   `<данные приложения>/no_backup` (Android не включает её в резервные копии). Нет метки или в ней
   другой id → база — копия: новый `node_id`, сброс водяного знака выгрузки, и **невыгруженные ops
   прежнего узла, всё ещё побеждающие в своих полях, записываются заново от нового узла** — иначе их
   никто не выгрузит (старое устройство могло пропасть). Ложное срабатывание (метку удалили) безвредно:
   лишний узел в папке и повтор значений.
   Альтернативы: аппаратный id (MachineGuid, ANDROID_ID) — нужен платформенный код, вернёмся в M6;
   распознавание по чужим чанкам в своей папке — срабатывает только после порчи.
5. **Часы при запуске** = max(сохранённые в `local_meta`, `MAX(hlc)` всего журнала), с id своего узла.
   Берём все ops, а не только свои: правка после перезапуска должна быть позже уже увиденных чужих
   (иначе LWW молча отдаст победу старому значению). `MAX` по строкам корректен: ширина полей времени и
   счётчика фиксирована, а часть узла нам не нужна. Часы сохраняются в той же транзакции, что и правка,
   и после каждой синхронизации.
6. **«Входящие»** — фиксированный id `00000000-0000-8000-8000-000000000001` и одинаковые на всех
   устройствах значения полей (`name: 'Inbox'`, показ — через l10n в M2): параллельное создание на двух
   устройствах даёт одинаковые значения — не конфликт.
7. **`Mutator`** — единственная точка записи из приложения: create (id из `IdGenerator`) / update /
   delete / restore / resolveConflict; объектные поля (`due`) сливаются с текущим значением из
   `field_versions` (ключ со значением `null` удаляет ключ). Сущность `conflict` напрямую не пишется.
8. **Сценарии синхронизации через папку — в `package:oplog_sync/testing.dart`** (как контракт M1.3):
   пакет гоняет их на памяти, приложение — на drift и временной папке на диске через `IoSyncFs`.
   Там же контракт `SyncFs` — один набор для `MemorySyncFs` и `IoSyncFs`.
9. **Провайдеры Riverpod**: `syncServicesProvider` задаётся в `main` через `overrides` после асинхронного
   запуска (база, reproject, узел, часы, «Входящие»); база, движок и `Mutator` — производные от него.
   Ошибка открытия (в т.ч. `SchemaTooNewException` из фонового изолята drift) — экран ошибки, база не
   трогается. Альтернатива: `FutureProvider` и `AsyncValue` в каждом потребителе — лишняя обработка
   «ещё грузится» по всему UI ради одной секунды при старте.

## Итог (23.10.2026)
- Приложение: 232 теста (test/sync — 66), пакет: 147, integration_test на Windows: 2. Мутационная проверка:
  восстановление часов (обе половины max), переиздание правок копии, очередь `IoSyncFs`, повтор `rename`,
  слияние срока, поля «Входящих», `COALESCE` аренды — без каждого падает свой тест.
- Сверх плана: защита часов в `MergeEngine.mutate` — мутационная проверка показала, что правка при отстающих
  часах пишется в проекцию с меньшим HLC: локально новое значение, на других узлах старое, навсегда.
- По ревью:
  - п. 4 изменён: переиздание правок копии — в движке (`MergeEngine.adopt`) с исходным временем и счётчиком,
    а не новой правкой «сейчас»: иначе устаревшая офлайн-правка обгоняла бы более новые чужие;
  - п. 6 изменён: «Входящие» пишут только `is_inbox` и `name` — новое устройство откатывало выбранный на
    другом вид (`view_style`) и создавало конфликт;
  - п. 7 изменён: известные ключи срока заменяются целиком (дата без времени убирает время), сохраняются
    только незнакомые;
  - `IoSyncFs.rename` повторяется, если файл ненадолго занят; сбой `info.json` — замечание в отчёте;
    `MemorySyncFs.writeStringIfAbsent` атомарен; аренда освобождается при сбое сохранения часов; JSON аренды
    без ключей считается свободной арендой.

## Обязательно в M2 (из ревью M1.4)
- **Запуск в одном экземпляре на Windows** (именованный mutex в runner, показ уже открытого окна — как
  Todoist): два экземпляра — два движка одного узла с разными часами; их ops ломают водяной знак выгрузки,
  и правки второго не выгружаются. Аренда защищает только синхронизацию. Рассмотреть водяной знак по
  локальному `rowid` вместо HLC как вторую линию защиты.
- **Смена папки синхронизации**: выгруженные ops выбывших узлов (в т.ч. прежнего id копии базы) живут только в
  старой папке — до снапшотов (M12) смена папки должна предупреждать или переносить их.
- Проверить `IoSyncFs` на настоящем OneDrive (повторы `rename`, временные файлы).

## Порядок запуска (`startSync`)
`openAppDatabase` → `needsReproject()` → `reproject()` → узел (метка/копия) → часы → `MergeEngine` →
`Mutator` → перезапись невыгруженных ops прежнего узла (если копия) → «Входящие».
