# Синхронизация без сервера — дизайн

## Цель
Два и более устройств одного пользователя (Windows, Android) сходятся к одному состоянию без
центрального сервера, при любом порядке и задержке доставки, с редактированием офлайн.

## Подход: op-log с LWW-регистрами на поле + HLC
Выбран вместо «синхронизации файла БД» (повреждение при одновременной записи) и вместо
state-based CRDT (большие снимки). Это проверенная схема «CRDTs for mortals» (Actual Budget):
каждое изменение — маленькое неизменяемое сообщение, слияние коммутативно, ассоциативно, идемпотентно.

### Свой пакет вместо готового
Готового Dart-пакета для синхронизации двух устройств без сервера нет (проверено на pub.dev, октябрь
2026). Ближайшие кандидаты — `crdt` / `sqlite_crdt` / `crdt_sync` одного автора (cachapa): дают
HLC и LWW на уровне строки и WebSocket-обмен «клиент ↔ сервер», где сервером может быть второе
устройство. Их минусы для нас: слияние по строке целиком (правка названия на телефоне и приоритета
на ПК затирают друг друга), нет транспорта через папку, редкие релизы.

Поэтому ядро — собственный чистый Dart-пакет `packages/oplog_sync` (без Flutter, drift и прямого
доступа к ФС; всё через интерфейсы). Это не изобретение нового алгоритма, а реализация известной
схемы (ниже) под наш формат. Плюсы: слияние по полям, один формат для папки и LAN, тысячи сценариев
гоняются обычным `dart test` за секунды, пакет можно опубликовать отдельно. Из `crdt` при желании
можно взять готовый класс `Hlc` как зависимость или образец.

### Op
```
op_id        UUIDv7                      уникален, для дедупликации
node_id      string                      устройство-автор
hlc          string "001761110400000:0003:node"   wall ms (15 цифр) : counter (4 hex) : node
base         string | null                 макс. hlc ops этой сущности от других узлов, известных автору
entity_type  task | project | section | label | filter | comment | reminder | task_label | completion | settings | conflict
entity_id    UUIDv7
field        string                      имя поля; "deleted" — tombstone
value_json   string                      JSON-значение (null допустим)
```
Создание сущности = набор ops по всем полям с одним hlc. Удаление = `deleted=true`.
Переупорядочивание = op на `order_key` (fractional index), конфликт одинаковых ключей разрешается
локально новым ключом (ещё один op).

### HLC (гибридные логические часы)
`tick()`: wall = max(now, last.wall); counter = wall == last.wall ? last.counter+1 : 0.
`receive(remote)`: wall = max(now, last.wall, remote.wall); counter по правилу Кулкарни.
Op, чей wall опережает локальные часы более чем на 1 час, не применяется и пишется в журнал ошибок
(защита от устройства со сбитой датой).

### Merge
Для (entity_id, field) хранится текущий hlc. Применить op ⇔ op.hlc > current.hlc (строковое сравнение,
при равенстве — больший node_id). Повторный op_id — пропуск. После применения — обновить проекцию.
Следствия: правка разных полей на двух узлах сохраняется целиком; правка vs удаление — побеждает позднее
по HLC; «воскрешение» = op `deleted=false`.

### Конфликты: решает пользователь
LWW сводит копии автоматически, но молча. Решение пользователя: параллельная правка одного поля
на двух устройствах (ни одно не видело правку другого) — это конфликт, о котором нужно сообщить
и дать выбрать вариант. Последовательная правка (телефон изменил → синхронизация → ПК изменил)
конфликтом не является.

Как отличаем: в op есть `base` — что автор знал о сущности: максимальный hlc ops этой сущности
от *других* узлов в его журнале (общий для всех полей одной правки). Автор X видел op Y ⇔
`X.base >= Y.hlc`. Две ops с разных узлов **параллельны**, если ни один автор не видел другую.
Конфликт — свойство каждой **пары** ops, без оглядки на третьи (`findConflicts` в пакете, чистая
функция), поэтому не зависит от порядка прихода, повторной доставки и `rebuildFromOps()`:
- параллельная пара на одно поле с разными значениями ⇒ конфликт вида `edit`;
- параллельная пара «tombstone + правка обычного поля» ⇒ конфликт вида `delete`;
- одинаковые значения — не конфликт; поля из `silentFields` (порядок) — не конфликт.
Почему не hlc значения поля: правка поля ничего не говорит о том, видел ли автор чужое удаление или
восстановление сущности, — пришлось бы искать третью op (restore), и результат начал бы зависеть
от порядка ops внутри пакета. Для двух устройств правило точное: ops каждого узла читаются по
порядку, поэтому «видел op узла с hlc ≥ X» означает «видел X». Для трёх и более возможен редкий
пропуск уведомления; на сходимость данных это не влияет.

Что происходит:
1. LWW применяется сразу — данные сходятся, проигравшее значение не теряется (stale op в журнале).
2. Запись `conflict` с детерминированным id = sha256(entity_id, kind, field, min(hlc), max(hlc)) в виде UUIDv8,
   поля: entity_type, entity_id, field, kind (edit/delete), op_id старшей и младшей.
   **Запись производная**: вычисляется из журнала, как проекция, и пересоздаётся `rebuildFromOps()`.
   Ops синхронизируют только `resolved`. Если бы сам конфликт создавался ops-ами, узел, заметивший его
   позже, записал бы `resolved=false` с более свежим hlc и «переоткрыл» уже разрешённый конфликт.
3. Уведомление («Конфликт: задача „Отчёт“, поле Название») и экран «Конфликты» с обоими вариантами,
   кто/когда, кнопки «Оставить этот» / «Оставить тот». Бейдж в сайдбаре.
4. Выбор (`MergeEngine.resolveConflict`) = обычная op на поле (автор видел обе стороны спора — это
   последовательная правка) + op `resolved=true` на все открытые конфликты этого поля.
   Доходит до второго узла и закрывает конфликт там же. Пока выбора нет — действует результат LWW.

### Проекции
Два уровня (реализация — `DriftOpStore`, lib/sync; схема — lib/data):
- `field_versions(entity_type, entity_id, field) → (hlc, value_json)` — победитель LWW каждого поля
  каждой сущности, включая поля и типы, которых эта версия приложения не знает.
- Таблицы `tasks`, `projects`, … — быстрое типизированное представление поверх `field_versions` для
  запросов и `watch()`. Поле op → колонки через реестр проекторов (lib/data/projection): имена колонок
  только из кода (белый список), значение не того типа → значение по умолчанию, исходное остаётся в
  `field_versions`. Инвариант: таблицы = реестр(`field_versions`).

`rebuildFromOps()` (`MergeEngine.rebuild`) очищает оба уровня и конфликты и применяет весь журнал заново
(кнопка в настройках, тест). `reproject()` перекладывает `field_versions` в таблицы без повторного LWW —
при смене версии реестра (`projector_version` в `local_meta`): так поля от более новой версии
приложения, пришедшие до обновления, попадают в свои колонки после него.

Срок задачи — одно поле-объект `due` {date, time?, tz?, …}: параллельная правка срока — один конфликт.
Проектор раскладывает его на `due_date`, `due_time`, `due_tz`; остальные ключи остаются в op.

### Специальные случаи
- Завершение повторяющейся задачи: ops `completion` (новая сущность: task_id, completed_at, due_was)
  + op на `due` задачи. Если оба узла завершили одно вхождение офлайн — две completion, срок по LWW;
  дубликат completion схлопывается по (task_id, due_was).
- Вложения комментариев: файл кладётся в `sync/blobs/<sha256>`; op хранит хеш и имя.
- Настройки пользователя — тоже сущность `settings` (одна, фиксированный id), чтобы тема/цели
  синхронизировались; локальные вещи (размер окна, путь к папке) — вне синка.

## Транспорт A: общая папка (основной)
Папка выбирается пользователем: OneDrive, Google Drive (на Android через SAF), Syncthing, любая.
```
<папка>/planner-sync/
  format.json                  { "v": 1, "folder_id": "<uuid>" }
  nodes/<node_id>/
    info.json                  имя устройства, платформа, последний seq, время
    000001.ndjson … 000042.ndjson   чанки ops (неизменяемы после записи)
    snapshot-<hlc>.ndjson      полный снимок состояния узла (для новых устройств и компакции, M12)
  blobs/<sha256>               вложения
```
Правила (реализация — `FolderTransport` в пакете):
- Узел пишет только в свою папку, чужие — только читает. Запись файла целиком через временный файл +
  rename (`SyncFs.writeString`).
- Каждая выгрузка — **новый** чанк с номером «максимальный существующий + 1»; больше ≈1 МБ — делится на
  несколько, но ops одной правки (общий HLC) всегда в одном чанке. Последняя строка чанка — `{"end": N}`
  с числом ops: без неё чанк считается недокачанным (обрыв мог прийтись ровно на границу строк).
  Существующий файл никогда не перезаписывается — даже после восстановления базы из копии.
  Альтернатива «дописывать открытый чанк до 1 МБ» отвергнута: облако чаще видит меняющийся файл, а
  читателю нужен курсор «файл + строка».
- Что уже выгружено — HLC последней своей выгруженной op («водяной знак»): HLC своих ops строго растёт.
  Если часы движка отстают от водяного знака (не восстановлены при запуске), синхронизация падает с ошибкой.
- Курсор `node_id → номер последнего применённого чанка` хранится локально в `sync_cursors`; смещение
  внутри файла не нужно, раз чанки неизменяемы. Курсоры и водяной знак привязаны к `folder_id` из
  `format.json`: другая папка (или пересозданная) — состояние сбрасывается, читаем всё и выгружаем весь
  свой журнал заново.
- Чанки узла читаются строго по порядку номеров. Курсор не двигается, и чанк перечитывается позже, если:
  следующего номера ещё нет (облако не докачало), нет `\n` в конце или строки `end` (докачивается), строка
  не разбирается, op чужого узла лежит не в своей папке или число ops не совпало с `end`, часть ops
  отклонена (часы автора впереди), файл не прочитался (заблокирован, не скачан). Проблема с одним узлом не
  мешает читать остальные и выгружать свои ops.
- На одну базу — один движок и один транспорт (иначе два экземпляра могут записать чанк с одним номером).
  Применение и сдвиг курсора — не одна транзакция: при сбое между ними чанк перечитается, дубликаты отбросит
  идемпотентность.
- Свою папку узел тоже читает по своему курсору: после восстановления базы из копии так возвращаются
  свои ops, выгруженные после копии.
- `format.json` с `v` больше поддерживаемого → синхронизация останавливается с ошибкой
  «обновите приложение», в папку ничего не пишется.

Цикл: при старте, по таймеру (Windows — 1 мин, Android — WorkManager 15 мин + при открытии), по
изменению файлов (watcher на Windows).
Компакция: узел, у которого все известные узлы прочитали чанк N, может заменить чанки ≤ N своим
снапшотом; tombstone старше 90 дней удаляются из снапшота.

## Транспорт B: LAN (дополнительный)
Обнаружение по mDNS (`_planner._tcp`), сопряжение QR/PIN → общий ключ; WebSocket, любой узел может
быть слушателем; обмен: «мой вектор (node → последний hlc)» → недостающие ops в обе стороны;
сообщения с HMAC. Используется, когда оба устройства в одной сети, не зависит от облака.

## Новое устройство
Выбрать папку → прочитать `format.json` → применить последний снапшот каждого узла + чанки после него →
создать свою папку узла. Если папки нет — создать с текущими данными (снапшот).

## Безопасность данных
Автобэкап БД перед миграцией и ежедневно (`backups/`, хранить 14). Перед миграцией — `VACUUM INTO`
(целостная копия и при журнале WAL), до миграций drift; сбой копии отменяет открытие базы; база новее
приложения не открывается. Файл базы — в папке данных приложения, не в «Документах» (OneDrive). Проверка целостности: пересчёт
проекций из ops раз в неделю на Windows в фоне с отчётом о расхождениях в лог.

## Инварианты реализации
Правила, которые проверяет каждое ревью и каждый тест слияния:
- Журнал `ops` — источник истины; таблицы сущностей — проекции. `rebuildFromOps()` восстанавливает
  их с нуля и покрыт тестом.
- Все записи в таблицы сущностей идут через один `Mutator` (lib/sync): он пишет ops и обновляет
  проекцию в одной транзакции. Прямые `update`/`delete` в таблицах сущностей запрещены.
- Удаление — только tombstone (`deleted=true`); связи many-to-many (например `task_labels`) —
  строки с tombstone. Порядок — fractional index; конфликт одинаковых ключей решается новым ключом.
- Время и ID не берутся из `DateTime.now()` и случайных генераторов напрямую: только инжектируемые
  `Clock` и `IdGenerator`, иначе слияние и тесты недетерминированы.
- Ядро `packages/oplog_sync` не знает о Flutter, drift и файловой системе; в lib/sync — только
  адаптеры, логика слияния в них не выносится.
- Изменение формата ops или файлов → bump `v` + миграция + тест чтения старого формата.
- Миграции drift идемпотентны; перед миграцией — автобэкап БД.
- При любом изменении слоя — тест с двумя in-memory узлами: параллельная правка разных полей;
  правка одного поля (конфликт с одним id на обоих узлах); последовательная правка (конфликта нет);
  правка vs удаление; разрешение конфликта на одном узле закрывает его на другом; оба завершили
  повторяющуюся; переупорядочивание; долгий офлайн одного узла; повторная доставка.
