Реализуй фичу: **$ARGUMENTS**

1. **Пункт ТЗ.** Найди фичу в docs/TODOIST_PARITY.md. Нет — добавь пункт в нужный раздел
   со статусом `[~]`. Если фича большая (несколько пунктов) — предложи разбивку и возьми первый.
2. **Поведение Todoist.** Если синтаксис/семантика неочевидны — используй агента parity-reviewer
   («опиши поведение Todoist для <фича>») до написания кода. Запиши факты в план.
3. **План.** Если затрагиваются 3+ файла или схема данных — агент architect. Сохрани план в
   docs/plans/<slug>.md. Открытые вопросы (не более 3) задай пользователю сейчас, а не в конце.
   Объясни пользователю ключевые решения плана (правило teaching.md).
4. **Данные.** Новые поля/таблицы — агент sync-engineer (миграция, ops, тест слияния).
5. **Логика и парсеры.** Реализуй в domain/nlp/features/logic с unit-тестами; примеры синтаксиса —
   в test/fixtures.
6. **UI.** Агент flutter-ui; платформенные части — platform-integrator.
7. **Проверка.** `dart run build_runner build -d` → `flutter analyze` → `dart format .` →
   `flutter test`. Для UI — `flutter run -d windows`, скриншот. Красное — исправить, не отчитываться.
8. **Ревью.** Агент code-reviewer на diff; затем parity-reviewer на фичу. Исправь блокеры и «важно».
9. **Закрытие.** Отметь пункт `[x]` в docs/TODOIST_PARITY.md, добавь строку в CHANGELOG.md,
   новые термины — в docs/GLOSSARY.md, коммит `feat(<область>): <что>` с выводом тестов в описании.

Отчёт пользователю: что сделано, блок «Что мы сделали и почему», какие расхождения с Todoist
остались и почему, что дальше по docs/ROADMAP.md.
