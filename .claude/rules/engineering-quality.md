# Инженерное качество

Применяй прагматично, а не как догму; при конфликте с требованиями или стоимостью изменения объясни
компромисс пользователю.

- одна ответственность и ясные границы; слабая связность между слоями (architecture.md), сильная — внутри;
- зависимости направлены к устойчивым абстракциям и передаются явно (конструктор, провайдер) — без
  скрытого глобального состояния и неявных побочных эффектов;
- небольшие связные изменения; рефакторинг — отдельным коммитом и только по конкретной причине;
- имена выражают намерение;
- невозможное состояние — сразу ошибка; ошибки не замалчиваются (dart-style.md);
- публичные контракты (`packages/oplog_sync`, интерфейсы lib/platform, формат ops) меняются осознанно —
  через Decision Gate;
- без преждевременных абстракций и функций «на будущее»;
- тестируемость — часть дизайна; каждое существенное изменение проверяемо тестом;
- писать как можно меньше и только в саму сущность: действие пишет поля, которые меняет, а производное
  (каскад, проект подзадачи, деревья) вычисляется при чтении — так правки двух устройств реже спорят;
- библиотеки и API — по актуальной официальной документации (docs/VERSIONS.md); устаревшие (deprecated)
  API в новом коде не используются; новая зависимость — стабильная версия с живым сопровождением и
  понятной лицензией, только с согласия пользователя.

Для каждой новой абстракции ответь:
1. Какую реальную вариативность она изолирует?
2. Почему существующей абстракции недостаточно?
3. Какую сложность она добавляет?
4. Можно ли её удалить без потери требований?

Ответы неубедительны — сначала предложи вариант проще.
